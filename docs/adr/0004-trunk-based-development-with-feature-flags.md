# Trunk-based development with feature flags for unfinished work

The team integrates every change into `main` at least once every two business days, even when the feature is incomplete. Unfinished features ship dark behind a feature flag that defaults to OFF, so `main` stays deployable and long-lived feature branches (with their merge drift and late integration risk) are avoided. Flags are a release mechanism only: authorization, auditing, encryption and consent are never gated by a flag, and an absent or unreadable flag resolves to the previous behavior. Backend flags are loaded once from environment variables into an injected struct, the frontend receives them from an authenticated backend endpoint so both sides always agree, and every flag is registered in `docs/FEATURE_FLAGS.md` and removed within 30 days of full rollout. The detailed standard lives in that document; this record captures why it was chosen over long-lived branches and over a third-party flag service for now, since clinical data must stay within the GCP Healthcare API boundary and a flag provider would add a new processor of operational data that is not yet justified.
