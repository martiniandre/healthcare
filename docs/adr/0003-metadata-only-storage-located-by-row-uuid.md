# Object storage located by record UUID; DB holds metadata and a display-only file name

We decided to store the physical location of clinical image files (DICOM studies and AI-analyzed exam files) only in the derived object key and never in PostgreSQL. The object key is rebuilt at runtime from the owning record's UUID: `{envRoot}/{module}/{patientId}/{rowId}.{ext}`, where `envRoot` is a storage root prefix carried in configuration (e.g. `prod/pacs`, `dev/exams`) and `{ext}` is taken from the sanitized original filename. The row's primary key IS the object locator, so no `gcs_path`/`file_path` column exists anywhere; a separate `file_name` column stores the human-readable original name (e.g. `sagittal_mri.dcm`) for display only and is never used to look up the object. Both modules go through the single shared `storage.StorageClient` (which now owns the bucket + environment root and exposes `Upload`, `GetPresignedURL`, and `Delete` taking a relative key), replacing the previous split where imaging wrote to GCS at `dicom/staging/{patient}/{uuid}.dcm` while exam_analyzer wrote raw files to the local `tmp/exam_uploads/` filesystem. Motivations: decoupling the DB schema from the physical storage layout so reorganizing folders or changing buckets requires no migration; eliminating the redundancy/risk of a stored full path diverging from reality; enabling per-environment roots inside one bucket; and unifying exam files into durable object storage with `Delete` instead of an ephemeral local purge (retention becomes a storage lifecycle policy). We accepted the trade-off that the leaf filename is not human-unique — uniqueness comes from the `rowId` folder segment — and that the storage layer must expose the extension explicitly since the object key is assembled from the row UUID plus a whitelisted extension read from the original filename.
